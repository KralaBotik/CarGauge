# Хранение обслуживания

CarGauge использует один локальный SQLite-файл `Library/Application Support/CarGauge/History.sqlite3`. У приложения и расширения разные задачи. Виджет получает только опубликованный снимок температуры через App Group. Журнал обслуживания, диагностику и координаты в общий контейнер приложение не передаёт.

## Миграция 0.8 → 0.9

0.8 использует `user_version=1`. Миграция создаёт таблицы версии 2 в транзакции, считывает старые JSON-события обследований и идемпотентно переносит их в типизированный журнал. Таблицы поездок, кадров, сырых PID, пропусков, событий и калибровки топлива сохраняются. WAL и история поездок продолжают использоваться. При ошибке SQLite транзакция откатывается. Нераспознанный старый отчёт остаётся в исходной таблице событий. Неизвестная более новая версия схемы открывается с явной ошибкой. Настройки подключения и порогов сохраняет прежний контейнер приложения.

| Таблица | Назначение |
| --- | --- |
| `health_state` | Контрольная точка движка, настройки правил, личные нормы, привязка ATRV к мультиметру |
| `monitoring_event` | Срабатывания и переходы, связанные по UUID проблемы, версия правила и ссылка на фактическую поездку |
| `diagnostic_receipt`, `dtc_scope`, `dtc_finding`, `dtc_history` | Полные ответы обследований и история DTC по статусу. Отсутствие ответа сохраняется в исходной записи |
| `maintenance_entry` | Компоненты, версии пользовательских интервалов, показания одометра и моточасов, работы с запчастями и осмотрами, заправки, настройки напоминаний |
| `maintenance_attachment` | Отдельные двоичные вложения с типом файла и идентификатором записи |
| `local_notice` | Устойчивые идентификаторы уже запрошенных уведомлений |
| `fill` | Принятые снимки калибровки 0.8 и 0.9. Пересекающиеся интервалы не учитываются повторно |

Одна запись обслуживания и её вложения меняются одной транзакцией. При удалении журнал требует подтверждения и удаляет только вложения этой записи. Следующие сроки отсчитываются от последней подходящей операции. Осмотр и долив сами по себе не меняют дату обязательной замены. Точное календарное основание хранится отдельно от точности пробега или моточасов.

Ручное показание одометра сохраняется отдельно от оценки на основе поездок. Отсутствие телефона может занижать оценку. Сроки, рассчитанные по пробегу, используют ручное значение. Моточасы показаны отдельно как значение владельца, наблюдавшееся время и дополнительный интервал, восстановленный по PID `011F`. Для оценки дополнительного времени объединяются пересекающиеся интервалы. Периоды со скачком системных часов исключаются. Учитываются только подтверждённые наблюдения и восстановимые границы. Начало наблюдения не означает фактический запуск.

## Резервная копия и объём

Полная копия создаётся через `VACUUM INTO`, включая уже зафиксированные данные из WAL. Отдельно требуется подтверждение, поскольку копия содержит исходную телеметрию, пользовательские записи и вложения. Автоматического импорта и восстановления поверх существующей базы пока нет. При установке сохраняйте прежний подписанный bundle ID и контейнер, а резервную копию храните отдельно. [Документация SQLite](https://sqlite.org/lang_vacuum.html#vacuuminto)

Размер файла и WAL виден в истории поездок. При импорте вложений действуют ограничения по формату и объёму на файл и запись. После удаления вложений SQLite может использовать освобождённые страницы повторно. История не удаляется по сроку. Замеры 0.8 для поездок и показаний приведены отдельно. Общий объём зависит от количества исходных кадров и фотографий. Длительные замеры на физическом iPhone для 0.9 ещё предстоят. [Замеры телеметрии](TELEMETRY_STORAGE.md)
